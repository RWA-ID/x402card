Company cards, run by name

Every card has a name. Run them all from your AI app.

Give each card your company issues, to an employee, a team or an AI agent, a name with its spend policy on it. Then manage it by name: “give maria $300 for the offsite”, “freeze sam’s card”. Anything over the limits goes to a manager by email. Nobody handles a card number.

→Manage by name

Your AI app is the card dashboard.

Connect X Card to Claude, ChatGPT or any MCP client and the cards answer to names. Ask who’s close to their limit, top up a budget, tighten a category, freeze a card. You never open a portal, and you never paste a card number.

Anything that loosens a card waits for its approver. They get the request by email and confirm with a code, or sign with a wallet if they have one.

  1. Issue to a name. maria, dev-ana, marketing, research-bot.
  2. Set the policy on the name. Per transaction, daily, monthly, merchant categories, verified payees.
  3. Name who approves. An email or a wallet. The exceptions go to them.

→Use cases

One card layer, any holder.

A name, a policy and an approver is all a card needs, whoever holds it. The same three things cover very different jobs.

maria.acme.eth

Employee spend

Travel, meals, software. A daily and monthly limit per person, and the manager approves the exceptions from their inbox.

research-bot.acme.eth

AI agents

Agents buy APIs, data and compute within a policy, pay only merchants whose name checks out, and freeze themselves on an anomaly.

marketing.acme.eth

Team and project budgets

One card per team or project, locked to its merchant categories. Close the project, freeze the name.

sam.contractors.acme.eth

Contractors

A short-lived card with a tight limit. When the contract ends, one sentence freezes it.

figma.vendors.acme.eth

Vendors and subscriptions

One card per SaaS vendor. A price hike over the limit pauses for approval instead of renewing quietly.

van-12.fleet.acme.eth

Fleet and field ops

Fuel and parts only, by merchant category, with a per-fill limit. Drivers never carry a shared card number.

offsite-lisbon.acme.eth

Events and per diems

A daily limit for each attendee during the event, and nothing after it.

lab-7.grants.uni.eth

Grants and stipends

Research grants, scholarships, allowances. Every rule is a public record anyone can audit, every top-up names who approved it.

In the demo, cards live under xcard.eth. A company would issue under its own ENS name, so cards read maria.acme.eth.

01Name → card

A name is the whole interface.

A card program issues the card. X Card attaches it to an ENS name, and from then on everything (paying, funding, freezing, checking the policy) goes through the name. The 16-digit number exists, but the person managing it, and any agent using it, never needs to see it.

02Policy lives in ENS

Limits are just text records.

Spend rules live on the name itself and are served by a signed ENS gateway, so any wallet, app, merchant or agent can read them. The records and the card’s controls are written together: what you read over ENS is what the card enforces.

03Pay

In-policy payments clear. The rest never reach the network.

The agent asks X Card to pay. The payment is checked against the ENS policy first, then the card program authorizes it against the same limits. A refusal tells the agent exactly which rule it hit, so it can adapt instead of retrying.

04Verified payee

Know who you’re paying.

Limits say how much. The payee check says who. A merchant’s ENS name lists the websites it takes payments on, and X Card reads those records before the card is charged. A lookalike checkout is blocked, and twice in ten minutes freezes the card. A merchant with no name waits for a human.

The records are the open x402 payee-name extension from x402 Identity Hub, so any name can opt in.

05Visa Trusted Agent Protocol

The merchant knows who’s paying.

At checkout, X Card signs the agent’s request with Visa’s Trusted Agent Protocol: an RFC 9421 signature over the merchant’s domain and path, tagged agent-payer-auth. The merchant checks it against X Card’s published key and serves a trusted agent instead of blocking a bot. X Card only signs a checkout it has already approved.

Two-way trust: the agent checks the merchant’s name, and the merchant checks the agent’s signature, both for the same domain.

07Kill switch

Anomaly in. Card frozen.

A burst of payment attempts, or a second try at a blocked merchant. The engine freezes the card at the card program and writes the status to ENS, so every resolver sees it at once. An agent can freeze its own card; only a human can unfreeze it.

→Under the hood

Real names. Real resolver. Sandbox money.

*.xcard.eth and *.x402card.eth resolve on Ethereum mainnet through an ENSIP-10 offchain resolver. The cards come from a card program behind one adapter interface; this demo uses the Airwallex sandbox, where card issuing is waiting on activation. Agents connect over MCP and never see a card number or an API key.

ENS · mainnet

OffchainResolver

Every lookup reverts with an EIP-3668 OffchainLookup. The contract checks the gateway’s signature before returning a record.

Gateway

Signed CCIP-Read

A Cloudflare Worker answers text() lookups from the card’s policy and signs each answer for five minutes. Card numbers and IDs are never stored in records.

Merchant identity · x402 payee-name

Verified payees

pay takes the checkout URL and the ENS name the merchant claims. X Card reads org.x402.origins on mainnet and applies card.payee: any, verified-or-escalate or verified-only. A held payment’s approval is bound to that exact merchant.

README · payee gate →
Agent identity · Visa TAP

Signed requests, published key

Ed25519 RFC 9421 signatures tagged agent-browser-auth or agent-payer-auth, 8 minutes, one use. The key is served as a JWK set and in the shape Visa’s reference merchant fetches; every signature is tested against a port of that verifier.

api.x-card.dev/keys →
Governance · Safe 2-of-3

No single key owns the root

The parent name and the resolver are owned by a 2-of-3 Safe, so re-pointing names, swapping the gateway or trusting a new signer takes two signatures. Escalated funding, looser policies and unfreezes need a human: the approver in card.approver, by an email code or a wallet signature.
